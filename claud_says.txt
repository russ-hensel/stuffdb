AlbumPictureSubTab / PhotoInShowModel -- why you're seeing extra columns
==========================================================================

Root cause
----------
In PhotoInShowModel.setup() (album_document.py):

    photo_id_col = self.fieldIndex( "photo_id" )   # = 5, in the plain photo_in_show table
    self.setRelation(
        photo_id_col,
        QSqlRelation( "photo", "id", "camera, dt_item, file, photo_id, sub_dir, name" )
    )

The third argument to QSqlRelation is documented as a single display column, but
Qt actually accepts a comma-separated list and SPLITS it -- it does not merge
those into one combined display value. The one relation you declared on column
5 gets replaced, at select() time, by 6 real columns pulled from photo.

I verified this empirically against data_sync/stuffdb.db (not just from memory
of the Qt source): after model.select(), model.columnCount() is 13, not the 8
you'd expect from photo_in_show's own schema (id, photo_id_old,
photo_show_id_old, sequence, photo_in_show_id_old, photo_id, photo_show_id,
photo_in_show_id).

Actual generated SQL (model.selectStatement()):

    SELECT photo_in_show."id", photo_in_show."photo_id_old",
           photo_in_show."photo_show_id_old", photo_in_show."sequence",
           photo_in_show."photo_in_show_id_old",
           relTblAl_5.camera, dt_item, file, photo_id, sub_dir, name,
           photo_in_show."photo_show_id", photo_in_show."photo_in_show_id"
    FROM photo_in_show, photo relTblAl_5
    WHERE (photo_in_show."photo_id" = relTblAl_5.id) AND (photo_show_id = <show id>)

Column-by-column mapping actually in the model (verified against a live row)
------------------------------------------------------------------------------
 0  id                      photo_in_show.id                (the bridge row's own id)
 1  photo_id_old            photo_in_show.photo_id_old       (legacy text id, unused)
 2  photo_show_id_old       photo_in_show.photo_show_id_old  (legacy text id, unused)
 3  sequence                photo_in_show.sequence           (real ordering field, editable)
 4  photo_in_show_id_old    photo_in_show.photo_in_show_id_old (legacy text id, unused)
 5  camera                  photo.camera                     (from the relation expansion)
 6  dt_item                 photo.dt_item                    (date taken, raw epoch int)
 7  file                    photo.file                       (filename)
 8  photo_id                photo_in_show.photo_id           (the REAL photo FK -- moved
                                                                here from its old index 5)
 9  sub_dir                 photo.sub_dir
10  name                    photo.name                       (photo's display name)
11  photo_show_id           photo_in_show.photo_show_id       (FK to this album)
12  photo_in_show_id        photo_in_show.photo_in_show_id     (legacy int, sample rows = 0)

None of columns 5-10 are still "relational" in Qt's sense -- I checked
model.relation(c) for c in (5, 8, 10): all report invalid except the original
index 5 slot, which is inert (no DisplayRole substitution happens; display and
edit values are identical for every column). So the QSqlRelationalDelegate on
the view has nothing to do here; this is just 6 plain extra columns tacked on.

Why the view currently shows all 13, all labeled "ix_col = N"
----------------------------------------------------------------
_build_gui() calls, in order:

    if debug_col:
        self.col_head_no()      # loops range(7) -- labels/widths only cols 0-6
    self.col_head_names()       # calls self.col_head_ix(), then `return`

col_head_ix() loops `for ix_col in range( model.columnCount() )` i.e. 0..12,
and sets every column's header to f"{ix_col = }". Since it runs after
col_head_no() and covers all 13 columns, it overwrites col_head_no()'s "0".."6"
labels and adds headers for columns 7-12 too. Net effect: you see all 13
columns, every header reading "ix_col = N", no column hidden, columns 0-6 at
80px width (leftover from col_head_no) and 7-12 at Qt's default width.

The column-name version of col_head_names() (ID / Seq / Name, hiding
photo_show_id and photo_in_show_id) is still in the file below the `return`
statement at line ~1263 -- it's dead code right now, never executes.

If useful: the fix is either (a) drop the comma-list trick and set the
relation's displayColumn to just "name", using photo_id_col_ix (now correctly
8, computed dynamically via _refresh_col_indices/fieldIndex so it already
tracks the shift) for the single friendly-name column, and do the separate
camera/dt_item/file/sub_dir lookups the way _photo_file_info_for_row() already
does for a query when needed -- or (b) keep the 13-column model but remove the
early `return` in col_head_names() (and the col_head_no()/col_head_ix() debug
calls) so the real header/hide logic runs, updated to use the already-correct
*_col_ix attributes for the new indices. Say the word if you want me to apply
either.


APPLIED FIX (2026-07-07)
==========================================================================
You picked "A" and asked to also stop seeing photo_id_old, photo_show_id_old,
and sequence.

Caveat on "not fetch": QSqlTableModel/QSqlRelationalTableModel always fetches
every native column of its base table (photo_in_show) -- there's no way to
selectively drop id/photo_id_old/photo_show_id_old/sequence/photo_in_show_id_old
from the query while still using this model class; they're what makes editing
(sequence, renumber_sequence(), submitAll()) work at all. So for those, the
lever is "hide from the view" (still fetched, still editable via code, just
not shown). What we COULD actually stop fetching was the relation's comma-hack
expansion (camera, dt_item, file, sub_dir) -- those genuinely aren't in the
query anymore now.

1. Plain "name" as the relation's displayColumn turned out to be unsafe: I
   tested it (QSqlRelation("photo","id","name")) and both DisplayRole AND
   EditRole return the friendly text "Daylily Norma Jean" -- the raw photo_id
   FK becomes unrecoverable from that column entirely. That would have broken
   _photo_id_for_row(), which reads EditRole at photo_id_col_ix to get the raw
   FK for the separate photo lookup query. So instead:

       QSqlRelation( "photo", "id", "name, photo_id" )

   -- a trimmed 2-item version of the old 6-item hack. "name" must come first
   in the list (it's the one that gets qualified with the photo-table alias by
   Qt's string concat; putting "photo_id" first would generate
   "relTblAl_5.photo_id", which errors -- photo has no such column). Verified
   against the live db: model.columnCount() is now 9 (not 13), fields are
   id, photo_id_old, photo_show_id_old, sequence, photo_in_show_id_old, name,
   photo_id, photo_show_id, photo_in_show_id. model.relation(5) ("name") is
   valid (real DisplayRole/EditRole substitution); model.relation(6)
   ("photo_id") is not -- it's a plain passthrough of the raw FK, exactly what
   _photo_id_for_row() needs.

2. _refresh_col_indices() now also computes name_col_ix, photo_id_old_col_ix,
   photo_show_id_old_col_ix, photo_in_show_id_old_col_ix (all via
   model.fieldIndex(), so they track wherever Qt actually puts them).

3. col_head_names() is no longer dead code -- removed the early `return` /
   col_head_ix() call, rewrote it to show only ID and Name, and hide
   photo_id_old, photo_show_id_old, sequence, photo_in_show_id_old, the raw
   photo_id column, photo_show_id, and photo_in_show_id. sequence is hidden
   but still fully fetched/editable -- you drive it via the resequence /
   move_top / move_after buttons, not by typing in the grid.

4. col_head_ix() (debug: number every column header) is kept as a manual
   opt-in -- _build_gui() no longer calls it automatically; there's a
   commented-out call right where col_head_names() runs if you need it again.
   col_head_no() (the old hardcoded range(7) version) was deleted -- it was
   already wrong for the current schema and fully superseded by col_head_ix().

Verified end-to-end against data_sync/stuffdb.db using the real
PhotoInShowModel class (not a rewritten stand-in): select_for_id(1037) ->
columnCount() == 9, visible columns == [(0, 'id'), (5, 'name')], row 0 name
via DisplayRole == "Daylily -- Stella in bod'", row 0 photo_id via EditRole ==
3313 (the real FK, not the name text).

Unrelated aside noticed while testing: stuffdb.py lines ~37-46 has an orphaned
